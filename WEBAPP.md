# NL-to-Action web app: how to run and use it

The web app puts the whole agent (Weeks 1–9) behind a browser UI with two tabs:

1. **Chat**: type a request in plain English. For every request you see:
   - the answer;
   - whether you may **modify the database** and why or why not;
   - **every SQL statement** the agent produced, whether it was executed, committed, rolled back,
     rejected, blocked or is awaiting approval;
   - the full **execution log**: Thinking → Action → Observation, including each statement of the
     sandboxed transaction.
2. **Database views**: three role-based views. Each role sees a different part of the database
   for a different job: a shopper's product catalogue, a support agent's customer accounts, and a
   DBA's operations-and-audit dashboard. Five records per page. The admin view is locked behind a
   password (`password`).

Everything runs locally: a Python web server (standard library only), the PostgreSQL demo database
in Docker (**2,000 line items** by default), and, if `GROQ_API_KEY` is in `.env`, the Groq LLM as
the SQL planner.

---

## 1. Prerequisites

| Need | Why |
|---|---|
| **Docker Desktop** (running) | hosts the PostgreSQL 16 demo database (`nl2action-pg`, port 55432) |
| **Python 3.10+** | the agent and the web server |
| a browser | the UI at http://127.0.0.1:8000 |
| a Groq API key in `.env` (recommended) | the LLM that writes the SQL; without one, an offline rule-based planner is used (see section 5) |

`.env` in the project root (it is git-ignored, so the key is never committed):

```
LLM_PROVIDER=groq
GROQ_API_KEY=gsk_...
# optional: GROQ_MODEL=openai/gpt-oss-20b
```

The server reads `.env` at startup. At startup it prints the variable **names** it loaded (never the
values) and the planner in use, for example `planner: Groq LLM · openai/gpt-oss-20b`.

No extra Python packages are needed beyond `requirements.txt`. The web server uses the standard library.

## 2. Quick start (one command, Windows)

Open PowerShell in the project folder (`D:\Tanisha\DBMS`), start Docker Desktop, then run:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\run_webapp.ps1
```

The script:

1. starts (or reuses) the `nl2action-pg` PostgreSQL container;
2. creates `.venv` and installs `requirements.txt` if needed;
3. loads the schema, the **2,000-line-item dataset** and all agent tables the first time;
4. starts the server and opens **http://127.0.0.1:8000**.

Options:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\run_webapp.ps1 -Reset      # restore the 2,000-row dataset first
powershell -ExecutionPolicy Bypass -File scripts\run_webapp.ps1 -Port 8080  # another port
```

Stop the server with **Ctrl+C**. The database container keeps running. To stop it as well, run
`docker stop nl2action-pg`.

## 3. Manual start (any OS)

```powershell
# 1. database (first time only; afterwards: docker start nl2action-pg)
docker run -d --name nl2action-pg -e POSTGRES_USER=agent -e POSTGRES_PASSWORD=agent `
    -e POSTGRES_DB=online_retail_db -p 55432:5432 postgres:16-alpine

# 2. Python environment (first time only)
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt      # macOS/Linux: .venv/bin/python ...

# 3. connection + schema/data (setup is needed the first time, or to reset the data)
$env:DATABASE_URL = "postgresql://agent:agent@localhost:55432/online_retail_db"   # bash: export DATABASE_URL=...
.venv\Scripts\python database\setup_demo_db.py                    # 2,000 line items (default)
.venv\Scripts\python database\setup_demo_db.py --dataset sample   # only the 13 original rows

# 4. web server
.venv\Scripts\python webapp\server.py              # http://127.0.0.1:8000
.venv\Scripts\python webapp\server.py --port 8080
.venv\Scripts\python webapp\server.py --reset      # reset the data, then start
```

If `DATABASE_URL` is not set (in the shell or in `.env`), the server uses the Docker demo database
URL above. At startup the server prints the URL, the `.env` variable names it loaded, the planner in
use and the admin password source.

### The data

| Dataset | Rows | Used by |
|---|---|---|
| **large** (default) | 123 customers, 215 products, 404 invoices, **2,000 line items** | the web app |
| **sample** | 3 customers, 13 products, 5 invoices, 13 line items | the Week 6–9 demos and the Week 9 evaluation (their expected outcomes are written for it; they reset to it themselves) |

The large dataset keeps the 13 original rows and adds the rest from `database/sample_data_large.sql`.
That file is generated by `database/generate_retail_data.py` (seeded, so it is identical on every
machine). The original Online Retail CSV is not in the repository, so the extra rows are synthetic
but follow the same shape:

- dates from Dec 2010 to Dec 2011, about 70% UK customers across 20 countries;
- Online Retail-style stock codes and product names, wholesale quantities and bulk discounts;
- 8% guest orders, 19 cancellation invoices (`C…`, negative quantities) and 3 bad-debt adjustments
  (`A…`).

They obey every constraint, trigger and business invariant. To regenerate with another size:
`python database\generate_retail_data.py --items 5000`, then `python database\setup_demo_db.py`.
After running a Week 6–9 demo, run `python database\setup_demo_db.py` (or `run_webapp.ps1 -Reset`)
to get the 2,000-row data back.

## 4. Tab 1: Chat

### Sending requests

- Type in the box at the bottom and press **Enter** (Shift+Enter for a new line), or click an
  example chip.
- **Dry run** (toggle, top right): writes are executed in the sandbox and every check runs, but the
  transaction is always rolled back. Use it to try changes safely.
- **New chat** starts a new session. Session memory, follow-ups like "delete them" and intent drift
  are all measured per session.

### Reading an answer card

| Part | What it tells you |
|---|---|
| **Status badge + headline** | `success`, `blocked`, `needs approval`, `rolled back` or `failed`, with a plain-English answer |
| **Database modification access** | the direct answer to "may I change the database with this, and why (not)?" |
| **SQL** | every statement, one box per attempt (see the states below), with the guardrail verdict, SQLSTATE and transaction id |
| **Result** | the rows returned (reads) or the rows changed (`RETURNING *` for writes) |
| **Why not** | ordered root causes: the stage that stopped the request, the concrete cause, and what you can do instead |
| **Notes** | retries, the blast-radius preview, intent drift, and where the undo SQL is stored |
| **Footer** | planner used, attempts, time, and the audit id (`python database/audit_log.py --request <id>`) |

Access panel states:

| Icon | Meaning |
|---|---|
| 👁 Read-only access | you only read data; the query ran in a `READ ONLY` transaction, so nothing could change |
| 🔓 Yes, you had write access | guardrails allowed it, all pre-commit checks passed, it was committed (undo SQL stored) |
| ⏳ Not yet, needs approval | a guardrail rule, the blast-radius preview or the drift detector requires a human decision |
| 🧪 Dry run | the change would succeed but was rolled back on purpose |
| ⛔ No | refused, with the reason: DDL, no filter, guardrail block, rejected by PostgreSQL (constraint/trigger), or a business rule broken before COMMIT |

SQL states. Blocked and failed statements are shown too, never hidden:

| Badge | Meaning |
|---|---|
| `executed` | read run inside a READ ONLY transaction |
| `committed` | write executed and committed |
| `rolled back` | write executed in the sandbox, then rolled back (check failed or dry run) |
| `failed` | sent to PostgreSQL and rejected (for example an FK violation, SQLSTATE shown) |
| `blocked` | stopped by the guardrails or the planner; **never sent to the database** |
| `awaiting approval` | planned and checked, not executed until you approve |

When the planner refuses a request before writing any SQL (for example `drop the invoices table` or
`delete all customers`), the card still shows the SQL the request would have needed. It is marked
**"reconstructed from your intent: never sent to the database"**.

### Approving a request

If a card says **needs approval**, it has an **Approve & run this exact SQL** button. Approving runs
exactly the plan shown, not a newly generated one, through the same guardrails, previews and
sandbox. Turn on **Dry run** first to approve it without committing. An approval can be used only
once.

### The execution log (right panel)

The log shows the selected answer's full trace. The newest answer is selected automatically; click
any earlier card to see its log.

| Entry | Content |
|---|---|
| **Thinking** | the agent's reasoning at each step (what it will do next and why: retry, stop, ask for approval) |
| **Action** | `generate_sql`, `check_guardrails`, `preview_blast_radius`, `detect_intent_drift`, `request_human_approval`, `execute_sandboxed` |
| **Observation** | the planner's plan and its explanation (with the SQL and the row-count estimate), the guardrail verdict and rules, the blast radius (cascades, predicted failures, triggers), the drift score and features, and the execution: every transaction statement (`BEGIN … READ ONLY/READ WRITE`, `SET LOCAL` timeouts, snapshots, `SAVEPOINT`, the statement, `COMMIT`/`ROLLBACK`) with its timing, every pre-commit check (✓/✗), and any captured PostgreSQL error |
| **Answer** | the final outcome |

Retries are grouped as **attempt 1, attempt 2, …**. The log shows the database error that was fed
back to the planner.

### Things to try

| Type this | You will see |
|---|---|
| `show customers from France` | read-only access, a SELECT executed in a READ ONLY transaction |
| `count invoices per country` | a JOIN + GROUP BY, read out as "country: count" |
| `find products with heart in the description` | text search (`ILIKE`) |
| `set the quantity of stock code 85123A on invoice 536365 to 7` | write access granted, COMMIT, 8 pre-commit checks, undo SQL |
| `delete invoice 536414` | the blast-radius preview reports the line item deleted by `ON DELETE CASCADE`, then the change is committed |
| `remove the product with stock code 84406B` | the preview predicts the FK failure, PostgreSQL rejects it with 23503, and "why not" explains it |
| `set the quantity of stock code 22752 on invoice 536365 to -2` | PostgreSQL accepts it, but a business invariant rolls it back |
| `show all customer ids with their country` | needs approval (customer identifiers), then **Approve & run** |
| `drop the invoices table` | blocked: DDL, with the reconstructed `DROP TABLE invoices` shown as never sent |
| `delete all customers` | blocked: no filter (`DELETE FROM customers` shown as never sent) |
| `show the line items of invoice 537967`, then `delete them` | intent drift: a read turned into a DELETE, so ALLOW becomes CONFIRM (try it in a **New chat**) |
| `set the quantity to 1 for every line item with quantity above 5` | blocked: over 1,000 rows would change (`ROW_LIMIT`); the UPDATE is still shown |
| `delete customer 12494` | needs approval twice over: customer identifiers (PII) and intent drift; the blast radius shows the SET NULL on their invoices |
| `top 5 products by revenue` *(Groq)* | a JOIN + SUM + ORDER BY written by the LLM |
| `how many orders were cancelled in 2011` *(Groq)* | a date filter and count, answered as "The answer is 17." |
| `which country has the most customers` *(Groq)* | "Result: United Kingdom (customer_count 84)." |

Committed changes really modify the data. Run `scripts\run_webapp.ps1 -Reset` (or
`python database\setup_demo_db.py`) to restore the 2,000-row dataset.

A bulk write the guardrails allow is committed. For example, `delete all cancelled invoices`
matches 19 invoices, which is under the 100-row confirmation threshold, and has a WHERE clause, so
it runs, and the cascade deletes their line items too. Turn on **Dry run** while experimenting with
deletes.

## 5. Planner: offline vs LLM

The ReAct loop, guardrails, previews, sandbox and explanations are the same in both modes. Only the
step that turns your request into SQL changes:

| Mode | When | What writes the SQL |
|---|---|---|
| **Groq LLM** (default when a key exists) | `GROQ_API_KEY` in `.env` or the environment | the Groq model (default `openai/gpt-oss-20b`) writes the plan. Its explanation appears in the log's Observation, labelled `[Groq LLM · model]` |
| **offline rule-based planner** | no key, or `PLANNER=offline` | `database/rule_planner.py` builds SQL from the Week 3 parsed intent: tables, filters, joins along foreign keys, GROUP BY aggregates, top-N, sorting, text search, month/year ranges, single-row INSERT/UPDATE/DELETE. Requests it cannot express get a clear "cannot express this" block. |

**Automatic fallback.** If a Groq call fails (no network, timeout, rate limit, or the model returning
a malformed tool call, which happens occasionally as `400 Bad Request`), the offline planner answers
that one request. The plan explanation says so:
`[LLM unavailable: …; offline planner used]`. Whatever planner wrote the SQL, it goes through the same
validation, guardrails and sandbox.

```powershell
# the key normally comes from .env; a shell variable overrides it
$env:PLANNER = "offline"          # force the offline planner even with a key
```

The header shows which planner is active (for example `planner: Groq LLM · openai/gpt-oss-20b`). The **Thinking** entries come from the agent's ReAct
controller. Its safety decisions (retry, stop, ask for approval) are deterministic on purpose and
are never delegated to the model. The model's own reasoning about the SQL appears as the plan
explanation in the Observation that follows `generate_sql`.

## 6. Tab 2: Database views

Use the switch at the top right to toggle between the three views. Each role sees a different part
of the database, for a different job, in a different layout. Each shows **5 records per page**,
with **Prev / Next**, **Refresh**, and "SQL used for this page".

| View | Audience · question it answers | SQL view · role | Layout and content |
|---|---|---|---|
| **User view** | Shopper: *what can I buy, what does it cost, what is popular?* | `v_user_catalogue` · `dbm_reader` | **Product cards** ranked by popularity: name, stock code, usual price (£), units sold, number of orders, a Bestseller/Popular badge. No customers, invoices or other people's orders. Postage/adjustment codes are excluded. |
| **Customer agent view** | Support agent: *who is this customer, do they need attention?* | `v_customer_agent_accounts` · `dbm_writer` | **One row per customer account**: masked id (`***16`), country, orders, cancellations, total spend, refunded amount, last order (and how long ago), and a **support flag** (VIP, VIP at risk, Has cancellations, Frequent refunds, At risk (inactive), OK). A **country filter** narrows the list. |
| **Database admin view** 🔒 | DBA: *what state is the database in, and what is the agent doing to it?* | `v_dba_activity` · `dbm_admin` + live `pg_catalog` | **Operations dashboard**: database size and version, row counts, agent requests and Week 9 escalations; live **business-rule health** (the four invariants with violation counts); agent requests by outcome and by verdict; **storage per table** (rows and size); then the **latest audited requests** with their exact SQL, Week 5 → effective verdict, status and root cause. |

The views are real PostgreSQL views (`database/agent_schema_web.sql`, applied by
`setup_demo_db.py`, or automatically at server start if missing). Each has a matching `GRANT` for
its role. The shopper and agent views share no columns, and only the admin view sees SQL or audit
data.

**Admin password:** `password`. Type it and click **Unlock**; **Lock** locks the view again. The
server checks the password on every admin request. To change it, set an environment variable
before starting:

```powershell
$env:WEB_ADMIN_PASSWORD = "something-else"
```

This password is a demo-level lock for a local app, not production authentication. The server
listens on `127.0.0.1` only.

## 7. HTTP API (used by the page)

| Method + path | Body / query | Returns |
|---|---|---|
| `GET /api/status` | | planner, database reachability, table counts |
| `POST /api/chat` | `{session_id, message, dry_run}` | status, headline, summary, `access`, `sql_log[]`, `steps[]` (the log), `result`, `why_not[]`, `notes[]`, `pending_id`, `request_id` |
| `POST /api/approve` | `{session_id, pending_id, dry_run}` | the same shape, for the exact approved plan |
| `GET /api/views/user?page=N` | | `{layout: "cards", columns, rows (5), total, page, relation, role, sql}` |
| `GET /api/views/agent?page=N&country=France` | `country` optional | `{layout: "table", …, countries: [{name, count}]}` |
| `POST /api/views/admin` | `{password, page}` | `{layout: "admin", …, dashboard: {tables, invariants, requests_by_status, …}}`, or `401` for a wrong password |

## 8. Troubleshooting

| Problem | Fix |
|---|---|
| `Port 8000 is already in use` | the app is already running (use that tab) or another program uses the port: `--port 8080` / `-Port 8080` |
| header shows "database not reachable" | start Docker Desktop, then `docker start nl2action-pg` |
| "The agent tables are missing" at startup | `python database\setup_demo_db.py` (with `DATABASE_URL` set) |
| header says "planner: offline rule-based planner (no GROQ_API_KEY …)" | put `GROQ_API_KEY=…` in `.env` in the project root (or set it in the shell) and restart the server |
| a plan explanation starts with `[LLM unavailable: …]` | Groq failed for that request (network, rate limit, or a malformed tool call); the offline planner answered instead. Send it again to retry the LLM |
| "offline rule-based planner cannot express this" | rephrase more simply (one table, explicit values such as `invoice 536365`, `stock code 85123A`), or use the Groq planner |
| only 13 line items after running a Week 6–9 demo | the demos reset to the 13-row sample: `python database\setup_demo_db.py` or `run_webapp.ps1 -Reset` |
| demo data changed after experiments | `scripts\run_webapp.ps1 -Reset` or `python database\setup_demo_db.py` |
| `docker run` says the name is in use | the container exists already: `docker start nl2action-pg` |

## 9. Tests

```powershell
$env:DATABASE_URL = "postgresql://agent:agent@localhost:55432/online_retail_db"
.venv\Scripts\python -m pytest tests\test_webapp.py tests\test_rule_planner.py -q
.venv\Scripts\python -m pytest -q          # whole suite
```

`tests/test_webapp.py` starts the real server on a free port. It checks static files, path
traversal, the admin password, read/blocked/approval flows and the 5-row views. Its sessions are
removed afterwards. It also checks that the three views are really different (no shared columns,
different layouts, working country filter). `tests/test_rule_planner.py` and
`tests/test_data_and_env.py` (generator rules, `.env` parsing, the Groq fallback) need no database.
The test suite never reads `.env`, so it never calls Groq.
